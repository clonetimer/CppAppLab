# W9 · A4 HTTP 请求准入与资源加固

## 从这里开始

1. 阅读 `include/http_hardening.hpp` 和 A1 解析器接口，先理解状态与字节边界。
2. 只实现 `src/http_hardening.cpp`，平台提供已完成的 A1 解析器与固定准入接口。
3. 先让正常完整请求通过，再处理尚未收完的输入；只有 Accepted 才交付请求。
4. 逐步添加头部字节数、字段数量、正文和单请求线长预算，区分语法错误与资源超限。
5. 在网页构建、运行测试、正式验收，并解释下一请求剩余字节如何保留。

## 目标

在已验证的 W9-A1 解析器上增加明确、有界、确定性的请求准入策略，不重复实现基础解析语法，不修改先前关卡。所有示例均在本地内存中测试，不向外部服务发送测试输入。它是教学用严格策略，不代表完整 HTTP 协议兼容性或生产安全认证。

## 你的任务

只编辑 `src/http_hardening.cpp`。只读接口为 `include/http_hardening.hpp`、`include/http_request_parser.hpp` 与 `include/http_message.hpp`。

| 合同 | 限制与行为 |
|---|---|
| 请求头 | 含结束空行最多 8192 字节，字段最多 32 个（不含请求行） |
| 解码正文 | 最多 65536 字节；完整合法头部声明的长度超限时立即拒绝 |
| 单请求线长 | 最多 98304 字节；只向解析器传入有界前缀 |
| NeedMoreData | consumed=0、空请求、不要求关闭 |
| Accepted | 只消耗首条完整消息字节、返回完整请求、不强制关闭 |
| BadRequest / HeaderTooLarge / PayloadTooLarge | consumed=0、空请求、必须关闭 |

判定优先级：先检查头部字节/字段预算，再由 A1 验证语法与分帧，然后检查 HTTP/1.1 非空 Host 及声明正文长度，最后判断未完成消息的线长或已完成消息的解码长度。A1 的头部/尾部字段区尺寸错误对应 HeaderTooLarge，正文尺寸错误对应 PayloadTooLarge，其余解析错误对应 BadRequest。头部到达字节上限仍无结束空行，已不可能在策略内完成。只要首条消息在预算内完成，后续任意后缀均不能改变该结果。分块正文未完成时受线长限制，完成时再检查解码正文长度。

失败与待接收状态不能暴露部分头部、正文或已消耗字节。close_connection 表示拒绝时策略强制关闭，并不是服务端完整的连接协商。成功与待接收都不能自动视为允许连接复用。

## 解释你的设计

为什么单条请求预算不等于接收缓冲区总预算？为什么含糊的分帧必须拒绝？为什么待接收时不能交付部分数据？实际服务器还需要如何处理截止时间、并发内存限制及关闭连接？

## 故障排查

- 合法请求因后面还有大量数据而被拒绝：检查是否误用整个缓冲区长度，应该只限制首条消息解析窗口。
- 数据没接收完却出现已接受状态：检查 A1 状态，不能直接暴露部分请求。
- 所有错误都成为普通语法错误：按照合同区分资源超限和格式错误。
- 声明了超限正文却一直等待：完整合法请求头解析后应检查声明长度，不必等待正文到齐。
- 分块正文已完成却超出策略：交付请求前检查实际解码正文长度。
