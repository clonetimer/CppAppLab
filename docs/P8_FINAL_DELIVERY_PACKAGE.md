# P8 Final Delivery Package

**Purpose:** one consolidated acceptance and handover package for the P8 browser-first C++ learning workbench. P8-C5 is treated as one integrated task; internal parallel work does not create separate user-facing deliveries.

## 1. Required delivery directory

The final release candidate must contain the following files and evidence:

```text
artifacts/p8-final/
  README.md
  acceptance/
    feature-coverage-matrix.csv
    course-coverage-matrix.csv
    ci-results.json
    recovery-test-report.md
  screenshots/
    cppapplab-workbench-desktop.png
    cppapplab-workbench-mobile.png
  engineering/
    DEVELOPMENT_EXPERIENCE.md
  release/
    merge-record.md
    package-manifest.json
    SHA256SUMS
```

The directory is assembled only from artifacts generated by the final accepted commit. Do not copy screenshots or package files from an earlier SHA into the final package.

## 2. Feature coverage matrix

`feature-coverage-matrix.csv` columns:

- `feature_id`: stable requirement identifier.
- `area`: navigation, editor, build, run, acceptance, history, service, recovery, responsive, accessibility, packaging.
- `requirement`: user-visible behavior.
- `implementation_paths`: relevant source/test paths.
- `automated_test`: exact test name or browser assertion.
- `ci_job`: exact workflow job.
- `result`: PASS / FAIL / NOT RUN.
- `evidence`: final commit, CI run or screenshot filename.
- `notes`: limitation or manual gate.

A feature is PASS only when implementation, automated test and final-commit CI evidence all exist. A test being present in source is not proof it passed.

The browser CI job runs `scripts/generate_course_coverage.py` from the authoritative catalog and uploads the generated CSV alongside the desktop/mobile PNG screenshots. Rows explicitly distinguish `catalog_browser_coverage`, `deep_journey_coverage` and `formal_acceptance`; the generator never marks a task PASS merely because it exists in the catalog.

## 3. Course coverage matrix

Generate rows directly from `course/tasks.tsv`; never hand-maintain a second list of course task IDs. Required columns:

- `task_id`, `week`, `title`, `task_type` (application / library-test / service), `prerequisites`, `browser_selectable`, `lesson_rendered`, `detail_api`, `state_label`, `state_reason`, `interaction_contract`, `deep_journey_test`, `formal_acceptance_test`, `result`, `evidence`.

The catalog sweep proves that all registered tasks are discoverable and accurately represented. Deep-journey coverage must be recorded separately. Never label all 23 tasks as deeply tested solely because all 23 were visited.

## 4. Desktop and mobile screenshot evidence

Capture from the real Chromium acceptance run on the final commit:

- `cppapplab-workbench-desktop.png`: 1440 × 1000 viewport, full-page screenshot at scroll origin.
- `cppapplab-workbench-mobile.png`: 390 × 844 viewport, full-page screenshot at scroll origin.

Record commit SHA, workflow run ID, browser/Playwright version, viewport and artifact name. Review both images for clipped controls, text overlap, horizontal page overflow, sticky-header artifacts and instructional/editor ordering. The editor may scroll horizontally internally; the page must not.

## 5. CI result ledger

Record every job from the final PR validation run and final post-merge main run:

- workflow name, run ID, event, branch, commit SHA, job name, conclusion, skipped steps and URL.
- Distinguish PASS, FAIL, CANCELLED and SKIPPED. Never convert skipped checks into PASS.
- Include GCC/GoogleTest, ASan/UBSan, clang-tidy, Chromium, Windows launcher, Ubuntu source/learner package builds and offline dependency bundle verification.
- Repository-wide formatting remains a manual gate unless it is explicitly executed and its result recorded.
- Ubuntu 22.04 source-build compatibility remains a push-only gate; record a push-run result or explicitly mark NOT RUN for the PR event.

## 6. Exception and recovery report

For each scenario record setup, injected fault, observed UI/API state, recovery action, final persisted state, child-process count and CI evidence:

1. C++ compile error → clickable diagnostic → source fix → build/run success.
2. Formal acceptance FAIL → NEEDS WORK → source/test fix → formal PASS.
3. Application run failure → retry without changing formal evidence.
4. Service child crash → FAILED and exit code → restart with fresh session.
5. Explicit service stop, task switch and web-server shutdown → process group reaped.
6. Browser refresh with dirty source → beforeunload prompt → cancel → explicit save → reload → exact source persistence.
7. Formal PASS → browser refresh → current state and append-only history retained.
8. Monaco CDN unavailable → offline textarea editing/autosave/build/run.
9. Request timeout or API interruption during an in-flight operation → clear UI state, no false success, safe retry.

A scenario not exercised by an automated test or documented manual test must be marked NOT RUN, not PASS.

## 7. Development experience archive

Copy the final `docs/DEVELOPMENT_EXPERIENCE.md` verbatim. Keep numbered lessons, reproduction, root cause, corrective design and regression test references. Add a final index mapping each lesson to the relevant PR/commit and regression test. Do not replace the detailed engineering record with a short retrospective.

## 8. Merge and release record

After the complete integrated PR passes:

1. Mark PR ready for review and merge only the exact tested head SHA.
2. Record PR URL, merge method, merge commit SHA, parent main SHA and merged timestamp.
3. Run the full required workflow against the merge commit on `main`; record the push-only Ubuntu 22.04 compatibility result.
4. Build source and learner packages for Ubuntu 22.04 and 24.04, plus offline dependency bundles.
5. Verify package manifest and SHA256SUMS; record filenames, sizes and checksums.
6. Verify the final artifacts are all derived from the merge commit.
7. Publish the handover README with install, launch, course start, offline setup, known limitations and support diagnostics.

## 9. Release acceptance rule

P8 is ready for handover only when:

- all 23 catalog entries are represented correctly;
- each of the 14 application profiles and 9 library/test-only tasks has the correct interaction contract;
- deep workflow and recovery coverage is reported separately from catalog breadth;
- final desktop/mobile screenshots are reviewed;
- final PR and main CI ledgers contain no unexplained failures;
- skipped/manual gates are explicitly listed;
- development experience and merge/package provenance are included;
- package checksums verify.

Do not claim Windows 11 + WSL2 target-machine acceptance unless it has been executed on that target. Do not claim full keyboard accessibility from the history-panel keyboard test alone. Do not claim all 23 lessons solved merely because the catalog sweep passes.
