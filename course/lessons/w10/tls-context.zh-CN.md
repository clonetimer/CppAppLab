# W10 · A1 TLS 上下文、证书信任与资源所有权

## 从这里开始

1. 阅读 `include/tls_context.hpp`，理解 Context 与 Session 的移动所有权和自动释放机制。
2. 只编辑 `src/tls_context.cpp`。先创建服务端上下文，再加载本地证书与私钥。
3. 配置客户端明确的 CA 文件、最低 TLS 版本与对端验证；在会话中设置预期 DNS 主机名和 SNI。
4. 运行固定测试，对照真实可信握手、错误主机名及无关 CA。无需启动网络服务。
5. 解释资源所有权、身份验证以及 W10-A2 需要进一步实现的传输状态机。

## 目标

学习 OpenSSL 3.x 资源的 RAII 管理、证书私钥一致性、客户端明确的信任锚和主机名校验。平台使用内存 BIO 对执行真实 TLS 握手及二进制应用数据传输。测试证书与私钥均在本机构建目录临时生成，不使用生产凭证。本关是上下文与身份组件，不是已部署的 TLS 服务。

## 你的任务

只编辑 `src/tls_context.cpp`。接口和测试证书生成方式由平台固定。

| 函数 | 合同 |
|---|---|
| make_server_context | 创建服务端上下文；最低 TLS 1.2，禁用压缩，加载 PEM 证书链/私钥并校验一致性 |
| make_client_context | 创建客户端上下文；相同版本下限，禁用压缩，仅加载明确的信任文件，启用 SSL_VERIFY_PEER |
| make_client_session | 已验证的客户端上下文、非空且不含 NUL 的 DNS 名（最多 253 字节）；设置客户端状态、主机名验证与 SNI；拒绝服务端或未验证上下文 |

失败返回空的拥有型句柄与明确错误类别。空参数或嵌入 NUL 对应 InvalidArgument，缺失或不一致的服务端身份对应 IdentityLoad，无法读取信任文件对应 TrustLoad；资源创建及协议/主机名设置错误独立分类。禁止关闭验证或回退到其他信任来源。固定夹具只验证本地主机及合成错误身份，不访问外部服务。双向证书认证、完整 DNS 语法验证、真实套接字事件调度、连接时限、有序关闭和 WebSocket 留给后续关卡。

## 解释你的设计

为什么可信证书链仍需要验证预期主机名？谁负责释放 SSL_CTX 与 SSL？为什么错误不能返回半配置的句柄？如何区分 WANT_READ/WANT_WRITE 与真正握手错误？为什么内存 BIO 握手不能证明 epoll 网络传输正确？

## 故障排查

- 证书或私钥加载失败：查看具体错误分类，检查 PEM 文件与密钥匹配；不要关闭验证。
- 无关 CA 或错误主机名也能握手：检查 SSL_VERIFY_PEER、SSL_CTX_load_verify_locations 与 SSL_set1_host。
- 握手需要更多输入：固定驱动交替处理双方，不把 WANT_READ/WANT_WRITE 当作致命错误。
- 找不到 OpenSSL 开发库：安装 libssl-dev 和 openssl，不需要更换全局编译器。
- 资源泄漏：每条错误路径都保留拥有型句柄的 RAII 自动释放。
