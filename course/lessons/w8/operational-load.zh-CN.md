# W8-D6-D3 · 运行负载、背压与持续运行验证

## 从这里开始

从一个客户端开始，逐步增加负载。

1. 用一个客户端运行固定回环探测，记录延迟和状态。
2. 增加到少量并发客户端。
3. 加入一个慢速读取的客户端，观察背压。
4. 重复发送 Keep-Alive 请求，监控连接数和队列的边界。
5. 运行短时间持续负载测试，比较前后的资源计数器。
6. 调查最先被破坏的不变量，而不只是增加超时时间。

**理解模型：**负载测试检查资源限制和生命周期规则在压力下是否依然成立。仅有较高的请求数量，并不能说明结果质量。


## 目标

验证 HTTP 服务器在并发客户端、慢速读取客户端、持续 Keep-Alive 流量和反复生命周期转换下的运行行为。这些测试旨在暴露资源泄漏、写入停滞、队列记账错误，以及贯穿完整 D5/D6 Reactor 流程的回归问题。

## 固定回环验收

### 1. 并发客户端与工作线程边界

一批独立回环客户端通过真实监听器和 Reactor 同时发送请求。

测试夹具验证：

- 每个请求都收到完整且符合预期的响应
- 处理器并发度大于一，且从不超过配置的工作线程数量
- 不超过有界的未完成任务容量
- 不丢失任何已接受连接、工作线程任务或响应
- 活动连接数和活动任务数的当前值指标恢复为零

该测试不要求达到特定的每秒请求数。调度行为和共享运行器的性能可能不同。

### 2. 慢速读取客户端引发的 TCP 背压

某个路由返回 8 MiB 响应，而客户端有意限制接收缓冲区并延迟读取。

测试夹具验证：

- 内核发送缓冲区已满时，服务器能够停止写入
- 对端开始读取后，EPOLLOUT 能恢复传输
- 完整正文逐字节一致地到达
- 只有完整序列化响应写出后，服务器才记录该响应
- 之后连接和工作线程的当前值指标能够恢复

这会验证实际的非阻塞 socket 路径；它不是模拟传输测试。

### 3. 持续 Keep-Alive 负载测试

八个并发客户端分别在各自的同一个持久 TCP 连接上顺序发送四十个请求，然后显式关闭连接。

测试夹具检查全部 320 个响应、响应顺序、零队列拒绝、零协议错误，以及活动连接、持久连接槽位和工作线程任务最终都能恢复。

该持续负载测试有意设置边界，以确保 CI 可重复。它是持续运行回归测试，不是生产容量基准，也不代表通过了多小时耐久性验证。

### 4. 反复运行服务器生命周期

测试夹具会创建、运行、使用、停止并等待八个独立服务器实例退出。每个实例请求停止两次以验证幂等性，然后检查销毁前连接和工作线程任务是否已处理完毕。

## 结果解读与边界

- CI 验证确定性的正确行为和资源恢复，不验证生产吞吐量、尾部延迟或容量 SLA。
- 自定义 Router 处理器在有界工作线程池中执行。处理器必须具有执行边界并能协作结束；任意回调都无法被强制取消。
- 服务器仍仅适用于 Linux。托管的 Ubuntu CI 不能替代 Windows 11 + WSL2 目标机器验收。
- 慢速读取行为的覆盖范围是 TCP 发送缓冲区边界。这不能证明 TLS、HTTP/2、chunked 传输或生产级负载均衡器的行为。

## 解释你的设计

1. 为什么工作线程并发度的限制应独立于已接受 TCP 连接数？
2. 慢速读取的客户端如何在非阻塞 TCP 服务器中产生背压？
3. 为什么只有仍有序列化响应字节待发送时，才必须启用 EPOLLOUT？
4. 为什么 Keep-Alive 持续负载测试能暴露单连接单请求测试可能遗漏的资源记账缺陷？
5. 为什么固定功能性负载测试不足以支持吞吐量或生产容量 SLA 的声明？
6. 在单独的基准测试中，你会收集哪些指标来报告吞吐量、p50/p95/p99 延迟、队列等待时间和错误率？

## 学习任务 — `w8.http-operational-load`

上面的集成 D6-D3 回归夹具验证服务器的运行行为。本学习任务构建可复用的负载探测客户端，使这些检查能够被复现并测量。

**工作区文件**

- `include/http_load_probe.hpp`
- `src/http_load_probe.cpp`

实现 `run_http_load_probe(const HttpLoadProbeConfig&)`。配置指定 IPv4 主机、TCP 端口、请求目标、并发客户端数量、每个客户端的顺序请求数、单次操作超时以及预期 HTTP 状态。每个客户端应在同一个 TCP 连接上顺序发送请求，并在最后一个请求中发送 Connection: close。

结果必须报告已尝试/成功/失败的请求数、经过的微秒数、每秒请求数，以及 p50/p95/p99 响应延迟。使用单调时钟。必须统计每一个尝试的请求，包括连接失败和非预期状态码。

**固定验收：**`course/fixtures/w8/http-load-probe` 中由平台维护的 5 项 GoogleTests。它们覆盖无效配置、单客户端测量、并发 Keep-Alive 资源恢复、非预期状态的统计以及连接失败。

```bash
./build/cppapplab start w8.http-operational-load "$HOME/cppapplab-work/w8-operational-load"
./build/cppapplab lesson "$HOME/cppapplab-work/w8-operational-load"
./build/cppapplab hint "$HOME/cppapplab-work/w8-operational-load" 1
./build/cppapplab check "$HOME/cppapplab-work/w8-operational-load"
```

负载探测器是测量工具，不承诺达到特定吞吐量。报告任何性能数字时，都应同时说明环境和工作负载。

## 故障排查

本学习任务提供 `run_http_load_probe`，不提供负载探测可执行程序。五项固定检查会提供回环服务器。

- **探测器在发送前就拒绝了配置：**检查 IPv4 地址、非零端口、以斜杠开头的目标、为正的客户端/请求数量以及超时。与无效配置用例比较，再通过夹具重试有效配置。
- **客户端在两次 Keep-Alive 请求之间停滞：**检查响应定界，以及客户端是否在等待 TCP EOF。重新检查按正文字节数处理 Content-Length、每个客户端使用一个连接，以及只在该客户端最后一个请求上使用 `Connection: close`。
- **失败请求从总数中消失：**比较已尝试请求数与成功加失败的总数，包括无法连接的客户端。重新检查非预期状态和连接失败用例；每个配置的请求尝试都必须计入统计。
- **延迟分位数或吞吐量明显不合理：**检查单调时间戳、微秒转换以及已排序的延迟样本。重新检查单客户端测量和分位数顺序，再随结果报告负载和环境，不要将结果当作容量保证。

## 验收要求

- [ ] 非法负载探测配置能够被明确拒绝，避免无意义请求。
- [ ] 单客户端请求能够得到正确的成功/失败统计。
- [ ] 多客户端 Keep-Alive 场景能够统计成功数及资源恢复情况。
- [ ] 预期状态码不匹配与连接失败能够计入失败请求，而不是丢失统计。
- [ ] 五项平台固定验收测试全部通过；报告测量条件，不将一次测试解释为生产吞吐能力。
