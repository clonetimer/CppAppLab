# W8-D6-C · HTTP 连接截止时间与资源配额

## 从这里开始

只有在不会无限占用资源时，Keep-Alive 才有意义。

1. 找出配置中的空闲、首部完成时间和请求数量限制。
2. 打开一个连接但不发送数据；观察空闲截止时间。
3. 只发送请求的一部分，观察首部截止时间。
4. 重复发送请求，直到达到单连接请求数量上限。
5. 测试慢速读取的客户端，并验证输出缓冲区仍有边界限制。
6. 确认超时清理发生在 Reactor 线程上。

**理解模型：**每个持久连接都会消耗描述符、内存和时间。截止时间与配额将这些开销转化为明确的限制。


## 目标

限制已接受 TCP 连接的存活时间和复用次数。Keep-Alive 不能让空闲 socket、缓慢发送的不完整请求或无限的请求序列变成没有边界的资源占用。

## 配置

`HttpServerConfig` 新增：

| 配置项 | 默认值 | 含义 |
|---|---:|---|
| `idle_timeout` | 30 s | 新接受的连接或空闲持久连接等待下一个请求字节的最长时间 |
| `header_timeout` | 10 s | 从收到第一个请求字节开始，完成请求行和首部所允许的绝对时限 |
| `body_timeout` | 15 s | 从完整首部块到达开始，完成请求正文所允许的绝对时限 |
| `max_requests_per_connection` | 100 | 一个 TCP 连接上最多可派发的请求数 |
| `max_persistent_connections` | 32 | 同时获准使用 Keep-Alive 的最大连接数 |

超时必须为正，且不大于 24 小时。请求数上限和持久连接上限必须为正。现有的 `max_connections`、`max_request_bytes`、`max_response_bytes` 以及工作线程队列限制仍然有效。

## 截止时间语义

- 已接受的 socket 首先使用空闲截止时间。
- 收到第一个请求字节时，切换到首部截止时间。
- 一旦出现 CRLFCRLF，但正文尚不完整，则切换到正文截止时间。
- 派发完整请求后，在处理器执行及响应写出的过程中，取消该请求的接收截止时间。
- Keep-Alive 响应完全写出后，派发下一个已缓冲请求；否则为连接设置新的空闲截止时间。
- 首部和正文截止时间是绝对截止时间，不是空闲计时器。逐字节发送不会延长它们。
- 空闲超时会静默关闭连接，因为此时没有待处理请求。
- 首部/正文超时返回 HTTP 408 Request Timeout，并携带 Connection: close。
- 对端半关闭仍遵循 D6-B：处理完已缓冲的完整请求；EOF 处的不完整请求收到 400，而不是继续等待超时。

实现使用一个 Linux timerfd，以及由事件循环持有的截止时间条目最小堆。截止时间变更或连接关闭后，通过连接的代次值使旧堆条目失效。反复使用 Keep-Alive 时，通过堆压缩限制过期条目占用的内存增长。

## 请求与持久连接配额

- 完整请求被接受并准备派发时，请求计数器递增。
- 配置所允许的最后一个请求的响应携带 Connection: close；之后的流水线字节都会被丢弃。
- 只有在请求本来会获得 Keep-Alive 时，才预留持久连接槽位。
- 如果所有持久连接槽位都已占用，仍然处理当前请求，但将其响应降级为 Connection: close。仅使用关闭策略的请求仍可获得服务。
- 预留的槽位在 TCP 连接实际关闭时释放，包括空闲超时、请求超时、对端断开以及显式关闭。

该配额有意独立于 `max_connections`：即使持久连接预算已满，仍可为仅使用关闭策略的短连接客户端提供服务。

## 故障排查

通过固定回环检查复现这些状态；学习者工作区提供的是服务器库，而不是独立应用程序。

- **缓慢逐字节发送阻止了超时：**检查进入首部或正文阶段时记录的单调时间戳。重新检查缓慢发送用例，不要在每次读取时刷新同一阶段的绝对截止时间。
- **空闲 socket 收到 408，或不完整请求被静默关闭：**检查是否已经收到任何请求字节，以及完整的首部终止标记是否已到达。重新检查空闲/首部/正文情况：空闲连接静默关闭；首部/正文到期发送 408 并关闭；不完整 EOF 仍为 400。
- **复用后的连接立即到期：**检查截止时间代次，以及响应完全写出后的状态转换。使旧条目失效，为下一个等待阶段设置新的截止时间，并重新检查空闲截止时间的刷新。
- **配额耗尽时拒绝有效工作，或配额始终无法恢复：**将派发计数、预留持久连接槽位与总连接数分开检查。重新检查最后一个请求的关闭行为和配额降级行为：先完成当前响应，再在 socket 实际关闭时释放槽位。

## 验收要求

固定回环测试夹具覆盖：

1. 静默关闭空闲连接。
2. 对不完整首部返回 HTTP 408。
3. 对不完整请求正文返回 HTTP 408。
4. 缓慢逐字节发送不会延长绝对首部截止时间。
5. 缓慢逐字节发送不会延长绝对正文截止时间。
6. Keep-Alive 响应完成后刷新空闲截止时间。
7. 达到单连接最大请求数时，在最后一个允许的响应之后强制关闭连接。
8. 持久连接配额使超出的 Keep-Alive 请求降级，并在关闭时释放槽位。
9. 拒绝无效的零超时和零配额配置。

该夹具在 GCC、ASan/UBSan 和 clang-tidy 下独立运行。D6-B 的八项 Keep-Alive 生命周期测试以及 D5 的单请求回归夹具仍作为独立门槛。

## 解释你的设计

1. 为什么空闲、首部和正文超时要划分为不同阶段？
2. 为什么首部/正文截止时间必须是绝对时间，而不能在每个字节到达后重置？
3. 为什么空闲超时会静默关闭连接，而不完整请求会收到 408？
4. 为什么持久连接配额要独立于已接受连接的总数上限？
5. 为什么持久连接槽位应在 socket 实际关闭时释放，而不是在请求一要求 Connection: close 时就释放？
6. 为什么最后一个允许的请求要先携带 Connection: close，然后服务器才丢弃后续流水线字节？
